# Gateway event plugins

Gateway plugins are local JavaScript modules that observe request metadata and
usage. They can implement dashboards, timing logs, and in-flight snapshots without
reading request bodies or parsing response streams again. These are server-side
plugins, separate from the Claude Code and OpenCode client integrations.

Set `COPILOT_API_PLUGINS` to a JSON array of module paths before starting the gateway:

```sh
export COPILOT_API_PLUGINS='["/absolute/path/monitor.mjs"]'
copilot-api start --port 5000
```

Relative paths resolve under `COPILOT_API_HOME` (the API home directory), rather
than the working directory. Restart the server after changing the list or plugin
code. Node.js and Bun load the same `.mjs` format; no npm package is required.
Modules run as trusted local code in the gateway process, not in a sandbox.

Each module default-exports a setup function:

```js
export default function setup({ version, server, on, log }) {
  log(`Plugin API ${version}, listening on ${server.port}`)
  on("request.end", (event) => {
    log(`${event.model ?? "unknown"}: ${event.durationMs} ms (${event.outcome})`)
  })
  return () => {
    // Optional shutdown cleanup. This can also be async.
  }
}
```

The API has `version: 1`, `server: { pid, port }`, `log(message)`, and
`on(eventName, handler)`. `on` returns an unsubscribe function. Setup and handlers
may be async. Events are immutable snapshots, delivered in order within each
plugin. Handler errors are logged without rejecting the request. Requests do not
wait for plugin I/O; synchronous JavaScript still shares the gateway event loop.
Each plugin queue holds at most 1024 pending handler invocations, then drops new
events with a warning. Shutdown drains queued events and runs cleanup, with a
two-second total deadline. There is no durable delivery or hot reload.

| Event | When | Data |
| --- | --- | --- |
| `request.start` | After authentication, before reading the body | Common request metadata, initially `model: null` |
| `request.model` | A handler has already parsed the requested model | Common metadata with the original requested model |
| `request.session` | Existing usage/session resolution identifies or updates the session while the request is active | Common metadata with `sessionId` |
| `request.first_chunk` | The first nonempty SSE body chunk passes through | Common metadata plus `firstChunkMs` |
| `request.end` | Body completes, errors, is cancelled, or the client aborts | Common metadata plus `durationMs`, `firstChunkMs`, HTTP `status`, and `outcome` |
| `usage.recorded` | The existing token-usage recorder emits an event | Existing usage fields plus `requestId`, `userAgent`, and `sessionId` |

Common metadata is `{ id, traceId, userAgent, sessionId, path, port, startedAt, model }`. `id` is a
gateway-generated request ID, independent of client-supplied trace IDs. `port` is
the configured listening port. `userAgent` is copied from the existing request
context and is an empty string when the header is absent. It is also included in
`usage.recorded` as plugin metadata, without adding a SQLite column.
`sessionId` reuses existing usage/session resolution: session affinity first, then
the explicit or fallback session already selected by the handler. It is null until
known. Header-derived affinity is available at start; payload/fallback-derived
sessions emit `request.session` when the existing usage recorder is created, even
before token usage is available. No new session ID is generated by the plugin
system. In `usage.recorded`, `sessionId` mirrors the existing `session_id` field
(empty becomes null); the original `session_id` remains unchanged.
`startedAt` is epoch **milliseconds**; durations use
the monotonic clock and are milliseconds. End outcomes are `completed`, `error`,
and `cancelled`. A cancellation before response headers has `status: 0`.
`firstChunkMs` is null for non-SSE/empty responses. It measures the first body
chunk, which may be a heartbeat or metadata event, rather than the first token.

Tracked endpoints are POST Chat Completions, Messages, Responses, and alpha search,
including existing provider-scoped and `/v1` variants. Authentication failures,
model discovery, and token-count requests are excluded. Model events reuse the
handler's parsed payload, including after zstd decompression, before model mapping.
Passthrough alpha-search routes that do not parse the payload keep `model: null`.
Request bodies, response content, and authentication headers are not event fields.

Usage keeps existing SQLite recording, trace/session IDs, and accounting unchanged.
Zero-usage events remain skipped. Usage may arrive during or after response cleanup;
join it by `requestId`, rather than assuming it always precedes `request.end`.

The example [monitor.mjs](../../../plugin/gateway/monitor.mjs) implements both a
per-process in-flight snapshot and monthly JSONL timing logs. Copy it to your API
home and configure `COPILOT_API_MONITOR_DIR` as its output directory. Timing records
include `user_agent` and `session_id`, and use `first_chunk_ms` to make the metric explicit. Readers should check each
snapshot's PID for liveness after crashes; live requests are not expired by age.
With `COPILOT_API_PLUGINS` unset, no plugins are imported and no lifecycle body
wrapper is installed. The gateway itself creates no telemetry output files.
