# Gateway event plugins

Gateway plugins are local JavaScript modules that observe request metadata and
usage. They can implement dashboards, timing logs, and in-flight snapshots without
reading request bodies or parsing response streams again. These are server-side
plugins, separate from the Claude Code and OpenCode client integrations.

Set `COPILOT_API_PLUGINS` to a JSON array of module paths before starting the gateway:

```sh
export COPILOT_API_PLUGINS='["/absolute/path/monitor.mjs"]'
copilot-api start --port 5000
```

Relative paths resolve under `COPILOT_API_HOME` (the API home directory), rather
than the working directory. Restart the server after changing the list or plugin
code. Node.js and Bun load the same `.mjs` format; no npm package is required.
Modules run as trusted local code in the gateway process, not in a sandbox.

Each module default-exports a setup function:

```js
export default function setup({ version, server, on, log }) {
  log(`Plugin API ${version}, listening on ${server.port}`)
  on("request.actual_model", (event) => {
    log(`${event.model ?? "unknown"} -> ${event.actualModel}`)
  })
  on("request.end", (event) => {
    log(`${event.model ?? "unknown"}: ${event.durationMs} ms (${event.outcome})`)
  })
  return () => {
    // Optional shutdown cleanup. This can also be async.
  }
}
```

The API has `version: 1`, `server: { pid, port }`, `log(message)`, and
`on(eventName, handler)`. `on` returns an unsubscribe function. Setup and handlers
may be async. Events are immutable snapshots, delivered in order within each
plugin. Handler errors are logged without rejecting the request. Requests do not
wait for plugin I/O; synchronous JavaScript still shares the gateway event loop.
Each plugin queue holds at most 1024 pending handler invocations, then drops new
events with a warning. Shutdown drains queued events and runs cleanup, with a
two-second total deadline. There is no durable delivery or hot reload.

| Event | When | Data |
| --- | --- | --- |
| `request.start` | After authentication, before reading the body | Common request metadata, initially `model: null` |
| `request.model` | A handler has already parsed the requested model | Common metadata with the original requested model |
| `request.actual_model` | Upstream dispatch selects or changes the resolved target | Common metadata with `actualModel` |
| `request.session` | Existing usage/session resolution identifies or updates the session while the request is active | Common metadata with `sessionId` |
| `request.first_token` | Existing stream parsing observes thinking start or the first nonempty model output | Common metadata plus `firstTokenMs` |
| `request.end` | Body completes, errors, is cancelled, or the client aborts | Common metadata plus `durationMs`, `firstTokenMs`, HTTP `status`, and `outcome` |
| `usage.recorded` | The existing token-usage recorder emits an event | Existing usage fields plus `requestId`, `userAgent`, `sessionId`, and `actualModel` |

Common metadata is `{ id, traceId, userAgent, sessionId, path, port, startedAt, model, actualModel }`. `id` is a
gateway-generated request ID, independent of client-supplied trace IDs. `port` is
the configured listening port. `userAgent` is copied from the existing request
context and is an empty string when the header is absent. It is also included in
`usage.recorded` as plugin metadata. SQLite and the usage events API additionally
store/expose `user_agent`, truncated to the first 64 characters; the plugin
`userAgent` metadata retains the original value.
`sessionId` reuses existing usage/session resolution: session affinity first, then
the explicit or fallback session already selected by the handler. It is null until
known. Header-derived affinity is available at start; payload/fallback-derived
sessions emit `request.session` when the existing usage recorder is created, even
before token usage is available. No new session ID is generated by the plugin
system. In `usage.recorded`, `sessionId` mirrors the existing `session_id` field
(empty becomes null); the original `session_id` remains unchanged.
`startedAt` is epoch **milliseconds**; durations use
the monotonic clock and are milliseconds. End outcomes are `completed`, `error`,
and `cancelled`. A cancellation before response headers has `status: 0`.

`model` stays the original client-requested model. `actualModel` is the resolved
target sent upstream after mapping, provider alias resolution, automatic model
selection, and endpoint normalization. For Google this is the model ID in the
request URL. It starts as null and emits `request.actual_model` at dispatch,
before waiting for the upstream response or token usage, so it is also available
for in-flight or failed requests without usage. Unknown targets and raw passthrough
routes keep it null. If a request selects different targets, the event repeats
when the target changes; subsequent lifecycle events carry the latest target.
This identifies the gateway's upstream target, not provider-internal routing.
In `usage.recorded`, `actualModel` aliases that usage event's existing `model`,
rather than a later target selected by another call. No SQLite column is added.

`firstTokenMs` measures time to the first observable thinking start or model output
(TTFT), from the same
post-authentication request start as `durationMs`. It includes upload/decompression
and upstream wait time. Existing stream parsers detect nonempty text, reasoning
text, or tool argument/input deltas. Explicit thinking starts count even without
exposed thinking text: Anthropic `content_block_start` with `type: "thinking"`,
Responses `response.output_item.added` with a reasoning item, and
`response.reasoning_summary_part.added`. Google parts with `thought: true` also
count. Initial Anthropic blocks with nonempty content, Google text parts, and
complete Google function calls still count. Whitespace counts as output.
Heartbeats, role declarations, empty deltas, signatures, usage, and generic
response/tool-start metadata do not trigger the event.
The event is emitted once, without forwarding output content to plugins or
reparsing the stream. Hidden thinking does not need to expose text if a start
marker is available. If the upstream emits neither a thinking marker nor content,
the gateway cannot observe when thinking began and waits for the first eligible
event. This is the arrival time of that event, not an internal model timestamp.
Non-streaming responses,
synthetic streams built from complete results, raw passthrough routes, and streams
that end without observable output keep `firstTokenMs: null`.

Tracked endpoints are POST Chat Completions, Messages, Responses, and alpha search,
including existing provider-scoped and `/v1` variants. Authentication failures,
model discovery, and token-count requests are excluded. Model events reuse the
handler's parsed payload, including after zstd decompression, before model mapping.
Passthrough alpha-search routes that do not parse the payload keep `model: null`.
Request bodies, response content, and authentication headers are not event fields.

Usage keeps existing trace/session IDs and token/cost accounting unchanged.
SQLite additionally stores request timing independently of plugin activation; see
[usage timing](usage.md#request-timing).
Zero-usage events remain skipped. Usage may arrive during or after response cleanup;
join it by `requestId`, rather than assuming it always precedes `request.end`.

The example [monitor.mjs](../../../plugin/gateway/monitor.mjs) implements both a
per-process in-flight snapshot and monthly JSONL timing logs. Copy it to your API
home and configure `COPILOT_API_MONITOR_DIR` as its output directory. Timing records
include `model`, `actual_model`, `user_agent`, `session_id`, and `ttft_ms`. Readers should check each
snapshot's PID for liveness after crashes; live requests are not expired by age.
The example batches snapshot changes and uses asynchronous file writes, so its
file I/O does not block request handling. While a snapshot write is pending,
changes are coalesced into the next snapshot of the latest state. Failed writes
retry automatically with exponential backoff capped at five seconds. Shutdown
cancels scheduled writes and retries, waits for the active write, then removes
the snapshot and temporary file, within the plugin runtime's shutdown deadline.
With `COPILOT_API_PLUGINS` unset, no plugins are imported or receive events.
The shared response wrapper still measures SQLite request timing with one
pull-through reader and no extra stream parsing. The gateway itself creates no
plugin monitoring output files.
